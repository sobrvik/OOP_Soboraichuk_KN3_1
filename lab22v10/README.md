# Лабораторна робота №22
## Тема: LSP: виявлення порушень і альтернативи
## Варіант 10: Співробітники (Employee & Volunteer)

### Мета
Поглибити розуміння принципу підстановки Лісков (LSP), навчитися ідентифікувати його порушення в ієрархіях класів та застосовувати альтернативні підходи для створення LSP-сумісних рішень.

---

## 1. Початкова ієрархія, що порушує LSP

### Структура
- Базовий клас: `Employee_Broken` з методом `CalculateSalary()`.
- Похідні класи:
  - `Volunteer_Broken_Throws` (кидає виняток у `CalculateSalary()`).
  - `Volunteer_Broken_ReturnsZero` (повертає `0` у `CalculateSalary()`).

### Клієнтський метод
`PayrollService_Broken.SalaryReport(IEnumerable<Employee_Broken> employees)`:
- приймає базовий тип `Employee_Broken`;
- викликає `CalculateSalary()` для кожного елемента списку;
- підсумовує загальний payroll.

---

## 2. Аналіз порушення LSP

### Який контракт базового класу порушується?
Базовий клас `Employee_Broken` має неформальний, але очевидний контракт:
- `CalculateSalary()` повертає валідну суму до виплати співробітнику;
- клієнтський код може без додаткових перевірок обробляти список `Employee_Broken` та розраховувати фонд оплати праці.

### Чому Volunteer порушує LSP?
Волонтер не отримує зарплату **в принципі**. Тому при підстановці волонтера в місце, де очікується `Employee_Broken`, виникають два типи проблем:

1) **Варіант з винятком (`Volunteer_Broken_Throws`)**
- `CalculateSalary()` кидає `InvalidOperationException`.
- Клієнтський метод, який працює зі списком `Employee_Broken`, аварійно завершується.
- Це змінює коректність програми при заміні базового типу на похідний → LSP порушено.

2) **Варіант з 0 (`Volunteer_Broken_ReturnsZero`)**
- Метод повертає `0`, але це **не означає**, що волонтера треба трактувати як “оплачуваного працівника з нульовою зарплатою”.
- У payroll-звіті волонтер виглядає як звичайний працівник, що спотворює бізнес-логіку та звітність.
- Отже, поведінка системи стає некоректною без явних помилок → теж LSP-порушення.

Висновок: `Volunteer` не є підтипом `Employee` з точки зору контракту “людина, якій нараховується зарплата”.

## 3. Альтернативне рішення (LSP-сумісне)

### Обраний підхід
**Зміна ієрархії + розділення контрактів.**

### Нова структура
- `IPerson` — спільний контракт для всіх людей (має `Name`).
- `IPaidWorker : IPerson` — контракт для тих, хто отримує зарплату (має `CalculateSalary()`).
- `Employee` реалізує `IPaidWorker`.
- `Volunteer` реалізує лише `IPerson` (бо зарплату не отримує).

### Чому це дотримується LSP?
- Клієнтський метод для зарплати (`PayrollService.SalaryReport`) приймає **тільки** `IEnumerable<IPaidWorker>`.
- Жоден клас, який не може виконати контракт "має зарплату", не потрапляє в цей метод.
- Тому підстановка будь-якого `IPaidWorker` не ламає логіку та не потребує спеціальних `if/try-catch`.

---

## 5. Висновки
- LSP важливий, бо клієнтський код має право покладатися на контракт базового типу.
- Якщо підклас не може підтримати контракт базового класу (як `Volunteer` для `Employee.CalculateSalary()`), наслідування є помилковим.
- Розділення контрактів (інтерфейси/абстракції за ролями) або композиція зменшують ризик LSP-порушень і роблять дизайн гнучкішим та зрозумілішим.
